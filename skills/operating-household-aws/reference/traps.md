# Traps from real HouseHold runs

Number = trap number in the old guide's §(b) (`household-infra/docs/runbooks/agent-aws-execution.md`, history) and `aws-lessons-log.md`, where the evidence is.

1. Raw `Cfn*` resources created in parallel can be rejected (CloudTrail vs bucket policy). Add `DependsOn`, or use L2 constructs.
2. AWS CLI v2 errors start with `aws: [ERROR]:`. Parsers must match that.
3. `aws sso login` fails from a deleted working directory. `cd` to a real directory, or use `--use-device-code`.
4. `aws sso login` selects no profile. Pass `--profile` and `--region` on every command.
5. Retained, fixed-name resources from a failed create block the retry. Their removal needs its own OK.
6. CloudTrail's first delivery lags. Use a bounded poll.
7. Enable termination protection only on `CREATE_COMPLETE` or `UPDATE_COMPLETE`.
8. Login setup: one `sso-session` named `household`; profiles `household-management|staging|production` share it.
   Check with `command -v aws; aws --version` first. Two CLI installs exist, and PATH order picks one.
9. `cdk bootstrap` runs from an empty temp directory, with the pinned CLI, checked against a `--show-template` digest.
10. Live synth is scoped to the stacks being deployed (`HOUSEHOLD_LIVE_SCOPE`).
11. Actions logs: read via `agent-token` only, in the job-log form of `household-infra/docs/runbooks/agent-token.md`. One `hous aws read` that fails with "Repository not found" from its own infra fetch: re-run the identical read once and record it; a second failure stops (HOUS-573 sitting3).
12. Check a dispatched run's branch and head sha before counting it.
13. S3 can show the old state for about a second after a create or delete. Retry before concluding.
14. A retry loop also retries when the read itself errors.
15. A lost `wait` result does not mean failure. Re-read the stack status.
16. GoDaddy nameserver change: confirm the second "Continue & Verify" step. A reload discards the change.
17. Never write into Sean's checkout, even to remove a stray file.
18. Sean-runs mode (packages READY before the switch): a package edited after READY needs a fresh READY before it runs.
19. zsh does not word-split `$list`. Use arrays or `${=list}`.
20. A hand-written fake agrees with a wrong script. Check key names against real CLI shapes (housetools `tools/aws/shapes/`; the old `household-infra/tools/package-fixtures` is frozen).
21. Zips built on different machines differ byte for byte. Pin CI's artifact, never a local build.
22. A long command can hit the tool time cap. Use resumable polling (`hous pkg run --detach` + `hous pkg wait` for a READY package).
23. ACM validation: poll `Certificate.Status` until `ISSUED`. The CLI waiter can time out first.
24. A package's assumed base template can be stale (a staging deploy was skipped). Read the live template first (checks.md step 3).
25. An HTTP API answers 404 where a REST API answers 403. Check the API type before asserting a status code.
26. A schema refresh with the worker's queue feed on dead-letters its tick messages (HOUS-618, 2026-10-10). End the sheet with the DLQ depth read and a decision. Disable the feed (the event source mapping), not the worker's concurrency: with concurrency 0 throttled batches return to the queue and their receive counts still climb, but a disabled feed receives nothing, so nothing dead-letters. While it is off, the tick-missing alarm (about 15 minutes), the oldest-message alarm and the throttle alarms email the alerts address; that is expected, and the run sheet says so before Sean approves.
27. Schema-chain cards: after a live DDL step, the next entry's practice preflight can refuse on a short-lived "pending household DDL job" and spend the card (HOUS-573, 2026-10-20). Put each live step on its own card, or run a `--verify-only` read showing `pending-household-jobs: none` before the next card.
28. Dead-letter reads in a run sheet: record the known depth before the sitting and pair the depth read with the oldest-message age (`ApproximateAgeOfOldestMessage`), so known old messages pass and only a new one stops (HOUS-573, 2026-10-20).
29. Web or app rows that need a sign-in: the run sheet names, for each such row, who types it, at which step and from where (Sean in the browser or app at step N using his tester list, or a protected in-process route; never argv), and Sean's directions name the Orca workspace and tab (HOUS-656, 2026-10-23).
30. Run-sheet prep: run `hous aws check` on every read the run sheet names, including each lookup that feeds a template placeholder and every read-back it asks for (an IAM policy, a log group name); a read with no recording is fixed in prep, by picking a recorded read that projects the same value or queuing the recording as code before the sitting, not mid-sitting (HOUS-573, 2026-10-27). Prep also validates each row's arguments without writing, using the tool's documented offline or check form or by reading its parser in the source (`hous help testers set` prints `--role T6`; a tester role is limited to T1-T9 and only the refusal says so, so a sheet names a sitting-only fixture file for higher labels); a row that writes is never run during prep. Prep takes each host in a link or URL from a delivered mail or a lookup, not from memory (HOUS-573 sitting3).
31. SQL for Sean is one idempotent run-all file extracted from the repo, never retyped, handed over with `pbcopy < <file>` or opened in his database viewer; never copied from chat and never block by block, because the chat display clips long lines (HOUS-573, 2026-10-27).
32. A schema card with an unrecognized `DROPS: ... reason not recognized by hous` line for a planned `ALTER COLUMN ... DROP NOT NULL`: read the SQL. If it removes no row, column or value (a constraint relaxation), proceed and name it to Sean in plain words. Any unrecognized line the run sheet does not list stops the sitting. The run sheet lists each expected `DROPS:` line by card (HOUS-573, 2026-10-30).
33. Between children of a sitting summary, a pending DSQL `ANALYZE` job on a household table can show in `--verify-only` after a live step although it is not the step's own job. Re-read `--verify-only` every 60 s for up to 10 min until `pending-household-jobs: none` before the next card; still pending at 10 min stops the sitting (extends trap 27; HOUS-573, 2026-10-30).
34. Every agent-owned staging inbox address must match an inbox receipt rule (`lib/staging-inbox-stack.ts`): only the sw2, sw3 and sw4 mailboxes and their plus labels. A made-up local part is accepted by the API but its mail is never stored. Check each address against the rules in prep (HOUS-573, 2026-10-30).
35. SQL handed to Sean never contains blocks meant to be skipped or "fallback" statements (extends trap 31): a select-all run applies them. Before a Sean-run setup tool, run its read-only probes in his viewer first (HOUS-573, 2026-10-30).
36. Prep rows: before telling Sean "ready", check that each prep row's output exists (folder, clone, file). The report's word "ready" is not the check (HOUS-573, 2026-10-30).
37. Tester and fixture sign-ins from one machine (the client IP, across all accounts, not per tester email) are at least 30 s apart (60 s for kept testers). The limit is about 3 sign-ins per 10 s per IP and path, so a fourth within about 10 s gets `429 auth.rate_limited`; wait it out (90 s worked) and keep the spacing in drivers and run-sheet rows (HOUS-573, 2026-10-30). Drivers share one sign-in clock helper that re-reads the stored clock before each sign-in (a stale state object saved over it once gave a 9 s gap). A web form clears its field after an answer, so a fill made right after the answer is wiped: fill after the answer settles. Prep dry-runs a driver against its form with no send (HOUS-573 sitting3).
38. Agent-made tester rows replace the old row, never add a second password line: Sean tried the old one and got "incorrect email or password". Hand Sean a password through the clipboard (`pbcopy`), not the chat (HOUS-573, 2026-10-30).
39. An event push goes to the current household members among the attendees, plus the creator if still a member, minus the account that made the change (household-api `eventRecipients`); the event API's `memberIds` takes USER ids, not household member ids (a wrong id is dropped silently). A push cue acts as a different account from the phone's, names the phone's account as an attendee and reads the attendees back, stopping if it is missing. A cue made with the phone account's own session gets no push by design. Triage a push miss from the outbox task's recipients and device outcomes before telling Sean anything (HOUS-573, 2026-10-30). On a real device a change push can also wake a backgrounded app, and its background sync then changes local state: on Nov 6 an event's "created" push let the app schedule a local reminder, which later fired on a locked member. Any reasoning about an app's local state counts background push wakes; never assume a backgrounded app has not run (HOUS-660 sitting2).
40. App flows run on a headless simulator by default: `simctl` plus XCUITest, no Simulator.app and no window (the old reading of this trap, "no Simulator app, no simulator leg", was wrong). Recipe, with the full detail in the lessons log entry "HOUS-573 sitting3 RN8":
    - own device (`simctl create`, `boot`); build with a throwaway scheme copy holding only the UI-test target with its TestAction on `Staging`, `build-for-testing`, then `test-without-building -parallel-testing-enabled NO` (without it xcodebuild runs on a "Clone 1 of ..." device and the app state is lost);
    - one long XCUITest as a command loop (the shell writes `cmd.json`, the test writes `res-<n>.json`; clear any stale `cmd.json` first); secrets go in by simulator pasteboard from a 0600 file and Paste, never `typeText`; the Mac HTTPS client is the second person;
    - a failed XCUIElement interaction aborts the whole driver: tap by coordinates from one frame snapshot, check `hasKeyboardFocus` before typing; once the app's own language picker saved a choice, only the picker changes it;
    - real APNs pushes arrive on the simulator; the OS background wake does not (the app stayed alive 2 minutes after Home), so it stays a real-device check (HOUS-573 sitting3).
41. The `apply-step --verify-only` read can be denied by the dsql-proof hook ("writes run only through hous aws run --apply") when typed as rule 3's header subshell plus `$HOME` paths and `| tail`. Keep the header anyway: SKILL.md rule 3's `AWS_*` clear and caller check apply to this read with no exception, and `hous aws whoami` does not stand in for them because it cleans only its own child process, not the shell that runs the read. If the hook denies the header form, stop, record it in `lessons-pending.md` and queue the hook or wrapper fix; never fall back to a plain form without the header. The cause (subshell, `$HOME` or pipe) was not isolated (HOUS-573, 2026-10-30).
42. Every step that only Sean may do stays his: AWS sign-in and OKs, the writes these rules keep as his (arm and disarm pastes, deploy buttons, his SQL, inbox setup), real-device-only behaviour (OS background wake, Camera QR handoff) and judgements in his own apps. App and browser flows are not his (registrar changes, such as GoDaddy nameservers, stay his): they run headless (trap 40). Every Sean step in a run sheet names why only he can do it, and a reviewer rejects a step without that reason (HOUS-573 sitting3). Its words are also checked in prep, and the reviewer rejects a Sean step that fails any of these (HOUS-660 sitting2):
    - every app screen, tab, button or label it names is checked against the app's strings or a simulator screenshot at the pinned iOS commit, and the sheet cites the file:line or the screenshot. A step said "the household name at the top of Home"; Home shows the user's name, and the household name is at the top of the Household tab;
    - every fixture it names says what it is and where to find it (tab, list or calendar, and date and time), for example 'the calendar event "Rows check" on tomorrow, Nov 7, 10:00 AM'. Sean: "calling it rows check is meaningless you didnt mention it was a calendar event or what day I could find it";
    - each edit is its own numbered line naming its tab and screen, and the report asks for each edit by name ("report each: saved or not"). Four edits in one sentence lost one, a required case that could not be redone after the deadline;
    - an offline step is preceded by an online step that opens each item the offline step will edit: the app reads offline only what an earlier online view cached, and shows "This content has not been downloaded yet." for the rest.
43. Never plan input by clipboard from the Mac to Sean's phone: Universal Clipboard does not reach it, and the Camera's QR button cannot copy a link. A scanned link opens the app, not Safari. `pbcopy` (trap 38) reaches his Mac only (HOUS-573 sitting3).
44. Production publish role: the arm paste, the publish button and the disarm paste are one step with a time bound. If no publish run has started within 15 minutes of the arm line, the coordinator asks Sean to disarm first (a role stayed armed about 17 h overnight). The publish PASS names the release job's `RESULT site-switch PASS` and `RESULT site-verify PASS`; publish-site has no separate verify job (HOUS-573 sitting3).
45. Run-sheet cleanup row: an inventory read of each household's members first, fixtures listed from the state file (never retyped), then delete order members, children, households, owner. Only the sole remaining member can delete a household. Run each delete guard once on a known fixture before the first delete (a guard read `name`; the API returns `household.name`) (HOUS-573 sitting3).
46. `log collect` from an attached iPhone needs root: `/usr/bin/log collect --device-udid <udid>` refused with "log: Must be root to collect logs from attached device" (exit 77), and agents never use `sudo`. Plan it as a Sean step (his own terminal; trap 42's reason: root on his Mac) or drop the row. Always call it by its full path: in zsh a bare `log` is a shell builtin, so the first call never reached the device (HOUS-660 sitting2).
